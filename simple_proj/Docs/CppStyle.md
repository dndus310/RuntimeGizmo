# Unreal C++ 구현 스타일

각 규칙은 기본 규칙을 먼저 쓰고, 필요한 경우 아래에 예외와 이유를 붙인다.

## 원칙 요약

- 작은 책임의 클래스와 함수로 나누고, 상위 함수가 처리 순서를 보여 준다.
- 파일 하나에는 "대상 + 역할" 하나를 담고, 이름은 대상을 앞에, 역할을 뒤에 둔다.
- 함수는 정해진 동사 어휘를 같은 의미로만 쓴다.
- 검증은 조건 변수로 모으고 반환은 한 번만 한다.
- 선언은 header에, 구현은 짝이 되는 `.cpp`에 둔다.
- 공개 계약(공개 API, BP 노드, 직렬화 필드)은 가독성을 이유로 바꾸지 않는다.
- 사용자는 한 번의 호출로 기능을 쓰고, 확장은 등록으로 한다.
- 구조를 바꾸는 리팩터링은 기준선 테스트와 단계별 회귀 검사로 동작이 같음을 확인한다.

## 1. 표기와 호환

- Unreal의 U/A/F/I/E 접두사, PascalCase, `b` boolean 접두사, UCLASS/UFUNCTION/UPROPERTY, 엔진 컨테이너·문자열·포인터를 쓴다.
  - 이유: 엔진 API와 표기가 섞이지 않게 한다. 가독성 정리를 이유로 C 스타일, snake_case, `std::` 컨테이너로 바꾸지 않는다.
- 공개 클래스·함수, BP 노드, 직렬화·JSON 필드, 이벤트 이름은 호환 계약이므로 이름만 정돈하려고 바꾸지 않는다.
  - 예외: 꼭 바꿔야 하면 CoreRedirects 등 이전 경로를 함께 제공한다.
- namespace를 쓰지 않는다. 이름 충돌은 프로젝트·모듈 접두사(`FMy`, `UMy`)와 역할이 드러나는 클래스 이름으로 피한다.
- 여러 파일이 공유하는 자유 함수는 static 함수를 가진 클래스로 묶는다. 한 파일 안에서만 쓰는 helper는 그 클래스의 private static 함수로 선언한다.
  - 이유: unity build에서 파일이 합쳐지므로 file-local static 이름도 모듈 안에서 고유해야 한다.

## 2. 파일과 폴더 구성

- 폴더는 계층으로 나눈다(`Core/`, `Model/`, `UI/`, `Thread/`). 한 기능 안에서는 단계나 대상 묶음으로 하위 폴더를 둔다(`Capture/`, `Restore/`, `Pipeline/`).
- 파일 하나에는 "대상 + 역할" 하나를 담는다. 파일과 클래스 이름은 대상을 앞에, 역할·변형을 뒤에 두어 같은 대상이 나란히 정렬되게 한다(`FilterBase`, `FilterSource`, `FilterWebcam`, `ModuleManager`).
  - 예외: 같은 대상의 작은 변형(이벤트 믹스인과 그 변형 클래스들)은 한 파일에 둘 수 있고, 클래스마다 짧은 구분 주석을 붙인다.
- 파일 이름은 점(`.`) 없이 PascalCase로 이어 붙인다.
  - 이유: UHT가 `<파일명>.generated.h`를 만들므로 UCLASS header에서 점은 문제가 된다.
- 파일 하나는 약 350줄 안팎을 기준으로 한다. 넘거나 서로 다른 단계의 함수가 섞이면 분리를 검토한다.
  - 예외: 화면 하나처럼 응집도가 높은 경우.
- header와 `.cpp`는 한 쌍이다. 선언만 있는 header는 만들지 않는다. 그런 선언은 직접 쓰는 주체의 header로 옮기고, 구현이 여러 `.cpp`로 나뉘면 클래스를 나눠 각자 쌍을 갖게 한다.
  - 예외: 여러 모듈이 공유하는 USTRUCT·UENUM 계약 header, 모듈의 `<Module>Types.h`.
- 일반 함수는 header에 선언하고 `.cpp`에서 정의한다. 짧은 Getter/Setter도 클래스 본문에 구현하지 않는다. 성능을 추측해 `inline`·`FORCEINLINE`을 추가하지 않는다.
  - 예외: template·`constexpr`처럼 사용 지점에 정의가 필요한 경우는 언어 계약을 따른다.
  - 이유: 소스 구성 원칙이다. 자동 인라인을 막으려고 `FORCENOINLINE`이나 최적화 비활성화 옵션을 추가하지도 않는다.
- 공개 header를 나누거나 옮길 때는 기존 include 사용자의 호환성을 고려한다.

## 3. 네이밍

- 클래스는 역할이 드러나는 명사로, 대상을 앞에 역할을 뒤에 둔다(`F…SnapshotBuilder`, `F…AdapterDispatcher`). 단계를 수행하는 클래스는 행위자 명사로 짓는다(`…Builder`, `…Restorer`, `…Collector`, `…Validator`, `…Tracker`).
- 함수는 짧은 동사로 시작하고, 아래 어휘를 같은 의미로만 쓴다. 이름에 And/Or로 서로 다른 동작을 묶지 않는다.

| 어휘 | 의미 |
|---|---|
| `Initialize` / `Release`, `Load` / `Update` / `Unload` | 생명주기 |
| `Begin…` / `End…`, `Pre…` / `Post…` | 짝을 이루는 구간 |
| `On…` | 외부에서 호출되는 이벤트 처리 |
| `Check…` / `Validate…` | 상태를 바꾸지 않는 검사 |
| `Try…` | 실패할 수 있는 시도 |
| `Find…` | 없을 수 있는 조회(nullptr 반환) |
| `Get…` / `Set…` | 접근자 |
| `Prepare…` | 실행 전 준비 |
| `Request…` | 비동기 요청 |
| `Dispatch…` | 여러 대상에 전달 |
| `To…` / `From…` | 변환 |
| `Count…` | 개수 |

- 접근자는 `Get…`/`Set…`을 쓰고 명사형 접근자(`Name()` / `Name(Value)`)는 쓰지 않는다.
- 멤버 변수에 `_`·`m_` 접두사를 붙이지 않는다.
  - 이유: UPROPERTY 이름은 Blueprint와 직렬화에 그대로 노출된다.
- 결과 변수는 의미 있는 이름으로 짓는다. 짧은 이름은 반복자와 짧은 블록의 지역 변수에만 쓴다.
- 자주 쓰는 포인터·컨테이너·함수 타입은 `<Module>Types.h`에서 `using`으로 이름을 붙인다(`using FMyObjectMap = TMap<UObject*, UObject*>;`).

## 4. 구조 설계

- 여러 단계로 된 기능은 단계마다 클래스를 나누고, 조율 클래스(Pipeline 등)는 단계 호출 순서만 보여 준다.
- 단계 사이에서 공유하는 서비스(월드, 옵션, 정책, 오류 출력)는 Context 구조체 하나로 묶어 전달한다.
  - 이유: 같은 참조를 여러 생성자 인자로 흩어 넘기면 의존 관계가 보이지 않는다.
- 같은 판정 루프(등록된 처리기 순회, 소유권 충돌 판정)가 반복되면 한 클래스에 모으고, 호출하는 쪽은 질문만 한다.
- 데이터(스냅샷, 결과)와 만드는 쪽(Builder), 쓰는 쪽(Restorer, Applier)을 분리한다. 데이터는 원본 수명에 의존하는 정보를 명시한다.
- 같은 종류가 여럿이면 `…Base` 기반 클래스를 둔다. 생성자는 `protected`로 숨기고 생명주기 가상 함수에 기본 구현을 제공하며, 구체 클래스는 필요한 단계만 재정의한다.
- 목록 관리와 순회는 `…Manager`·`…Center`·`…Registry`가 맡는다. 등록(`Append`/`Register`), 처리(`Process`/`Update`), 제거(`Remove`/`Unregister`)를 한 클래스에 둔다.
- 모듈마다 `<Module>Types.h`에 전방 선언, 타입 별칭, 공용 enum을 모은다. 다른 header는 이 파일을 include하고, 구체 header는 `.cpp`에서 include한다.
- 엔진이 이미 제공하는 기능(직렬화, 참조 교체, 객체 복제, 서브시스템)이 있는지 먼저 확인한다.
  - 예외: 직접 구현한다면 엔진 기능을 쓰지 않은 이유를 주석으로 남긴다.

## 5. 함수 구성

- 함수 하나는 한 가지 역할을 맡는다. 상위 함수는 검증·조회·처리 함수의 실행 순서를 조율한다.
- 초기화·등록, 캡처·생성·복원, 구성·갱신, 파싱·직렬화처럼 함께 읽어야 하는 단위로 나눈다.
  - 예외: 한두 문장을 감추려고 helper를 늘리지 않는다. 짧고 하나의 의미인 논리식·기본값 선택도 함수로 쪼개지 않는다.
- 선행 조건 검사와 대상 조회를 앞에, 검증된 데이터를 쓰는 실제 처리를 아래에 둔다. 선행 조건, 조회, 처리, 반환은 빈 줄로 구분한다.
- if/for/while에는 중괄호를 쓴다. 남는 return/continue/break는 별도 줄에 둔다.

## 6. 검증과 예외 처리

- 조건마다 `if (...) { return false; }`를 나열하지 않는다. 의미가 드러나는 `const bool` 지역 변수에 조건을 `&&`/`||`로 모으고, 그 값으로 작업 수행 여부를 정한 뒤 함수 끝에서 한 번 반환한다.
- 실패 이유는 if/else-if 체인으로 첫 번째로 실패한 조건 하나만 기록한다.
- short-circuit 순서로 포인터 검사가 역참조를 보호하게 하고, 부수 효과가 있는 호출의 순서를 보존한다.
- 실패할 수 있는 단계는 `&&`로 잇는다. 반복문은 `bOk = bOk && Step(Item);`으로 누적해 실패 뒤 단계를 호출하지 않는다.
  - 주의: 누적 플래그를 다시 대입할 때 이전 실패를 덮어쓰지 않는지 확인한다.
- 정상적인 부재도 조기 반환 대신 조건 변수와 `if` 블록으로 처리한다.
- 복구 가능한 설정 오류는 `ensureMsgf`로 알리고, 내부 불변 조건은 `check`로 검사한다.
- 스폰·트레이스 등 실행 결과는 실행 후 검사한다.
  - 이유: 종료·실패 경로의 필수 정리를 생략하면서까지 검사를 앞으로 옮기지 않는다.

```cpp
bool FMyTargetValidator::Validate(const AActor* Target, const UWorld& World, FString& Error)
{
    const bool bValid = IsValid(Target);
    const bool bAlive = bValid && !Target->IsActorBeingDestroyed();
    const bool bInWorld = bAlive && Target->GetWorld() == &World;

    if (!bValid)
    {
        Error = TEXT("The target Actor is no longer valid.");
    }
    else if (!bAlive)
    {
        Error = TEXT("The target Actor is being destroyed.");
    }
    else if (!bInWorld)
    {
        Error = TEXT("The target Actor belongs to another world.");
    }
    return bInWorld;
}
```

```cpp
bool FMyPipeline::Run()
{
    const bool bPrepared = Initialize() && Collect() && Capture();
    const bool bCompleted = bPrepared && Execute();
    if (bPrepared && !bCompleted)
    {
        Rollback();
    }
    return bCompleted;
}
```

## 7. 검사 비용과 수명

- 검사는 세 종류로 나눈다.
  - 사전 검사: 상태를 바꾸기 전에 한 번만 한다.
  - 경계 검사: 사용자 코드(콜백, 구성 스크립트, 델리게이트)가 실행된 직후, 그리고 공개 진입점과 프레임을 넘긴 참조에서 한다.
  - 중복 검사: 같은 동기 흐름에서 이미 보장된 내용은 다시 검사하지 않는다.
- 상태를 바꾸지 않는 사전 검사 경로(`CanXxx`)를 제공할 수 있게 검증과 실행 단계를 분리한다. 사전 검사는 이름 번호·카운터처럼 실행 때만 소비할 자원을 쓰지 않는다.
- 반복문 안에서 컬렉션 전체를 다시 훑지 않는다. 같은 대상을 여러 번 판정하면 작업 단위 캐시를 둔다.
- 오류 출력 인자(`FString& OutError`)는 첫 번째 실패만 기록하고, 이후 단계가 덮어쓰지 않게 한다.
  - 이유: 테스트와 호출자가 오류 문자열을 검사하므로 문자열 자체도 계약이다.
- 실패 시 정리할 대상(생성한 Actor, 등록한 델리게이트, 시작한 비동기 작업)은 만들 때 기록하고, 실패 경로 한 곳에서 일괄 정리한다.
  - 예외: 사용자 코드가 만든 외부 부작용은 되돌릴 수 없음을 주석으로 밝힌다.
- 람다가 `this`나 인덱스를 캡처해 델리게이트에 바인딩되면, 수명이 어떻게 보장되는지 선언 근처 주석으로 적는다.
- 사용자 콜백을 호출한 뒤에는 이전에 얻은 포인터와 소유자가 유효한지 다시 확인한다. 조율 객체 자신이 콜백 안에서 해제될 수 있으므로 재진입 가드를 둔다.

## 8. 공개 API와 확장 지점

- 사용하는 쪽에 생성·초기화·Tick·정리 절차를 요구하지 않는다. 수명은 서브시스템 등 엔진 수명 주기에 맡기고, 한 번 호출로 쓰는 진입점(Blueprint 함수 라이브러리 등)을 제공한다.
- 진입점은 성공 여부, 실패 이유, 생성한 결과 전체를 담은 결과 구조체를 반환한다.
- 타입별 특수 처리는 코어에 하드코딩하지 않고 등록형 확장 지점(정책, 규칙, 처리기)으로 만든다. 기본 제공 동작도 같은 API로 등록한다.
  - 이유: 사용하는 쪽이 하위 클래스 규칙으로 기본 동작을 덮어쓸 수 있어야 한다.
- 확장 지점은 깊이별로 둔다: 프로퍼티 포함 여부(람다 하나) → 대상 허용 규칙 → 클래스 자체 인터페이스 → 전체 처리기. 가벼운 확장으로 충분하면 무거운 확장을 요구하지 않는다.
- 클래스 계층 규칙은 등록 순서와 관계없이 가장 구체적인 클래스부터 적용하고, 결정을 미루는 값(unset, Defer)으로 상위 규칙에 넘길 수 있게 한다.
- 확장 인터페이스 header에는 콜백 호출 순서와 각 콜백에서 해도 되는 일·하면 안 되는 일을 적는다.

## 9. 선언 배치

- 전방 선언 → Delegate 선언 → 클래스 순서를 따른다.
- 클래스 안에서는 함수 영역 다음에 변수 영역을 둔다. 같은 접근 수준이어도 함수 블록과 변수 블록은 접근 지정자를 다시 써서 나눈다.
- 각 접근 지정자 안에서는 public using → 생성자 → virtual → 일반 함수 순서로, UFUNCTION을 우선한다. 기반 클래스의 생성자는 `protected:` 블록 맨 앞에 둔다.
- 함수 그룹은 초기화·세팅·진입 → 업데이트·갱신 → 삭제·리셋 → On 바인딩 → Getter/Setter 순서로 둔다.
- UFUNCTION이 아닌 함수 선언 사이에는 빈 줄을 두지 않는다. 설명 주석은 선언 바로 위에 붙인다.
  - 예외: 맨 앞 생성자(소멸자가 이어지면 소멸자까지) 뒤에는 빈 줄 한 줄을 둔다. 접근 지정자 블록 사이의 빈 줄은 유지한다.
- UFUNCTION 선언은 블록마다 빈 줄로 구분한다. 설명 주석이 있으면 주석 앞에 빈 줄을 두어 주석·UFUNCTION·함수를 한 블록으로 묶는다.
- 변수는 UPROPERTY 우선, 포인터 → 사용자 정의 타입 → 프리미티브 순서로 둔다. 멤버 기본값은 선언 순서와 같은 생성자 초기화 리스트로 작성한다.

```cpp
public:
    FMySelectionTracker();

    virtual void Tick(float DeltaTime) override;
    /** @brief 선택 기록만 지우고 현재 선택은 유지한다. */
    void ResetHistory();
    AActor* GetSelection() const;

    UFUNCTION(BlueprintCallable)
    void UpdateSelection();

    /** @brief 저장된 선택 상태도 함께 초기화한다. */
    UFUNCTION(BlueprintCallable)
    void ClearSelection();
```

## 10. 주석과 인코딩

- 함수·클래스 설명 주석은 `/** @brief ... */` 형식으로 쓴다.
- 주석은 한국어로 작성한다.
  - 예외: 식별자, 엔진·API 이름, 로그·에러 메시지 문자열은 원래 표기를 유지한다.
- 주석에는 코드만으로 알기 어려운 이유(수명, 실패 정리, 호환성)를 쓴다. 함수 이름을 반복하는 주석과 장식 구분선은 쓰지 않는다.
- 호출 스레드, 호출 시점, null의 의미처럼 사용자가 지킬 조건은 선언 바로 위에 한 줄로 적는다(`/** @brief 게임 스레드에서만 호출한다. */`).
- 기존 파일의 인코딩(BOM 유무 포함)과 줄바꿈은 바꾸지 않는다. 한글을 처음 넣는 소스 파일은 UTF-8 with BOM으로 저장한다.
  - 이유: BOM이 없으면 컴파일러가 시스템 코드 페이지로 읽어 한글이 깨질 수 있다.
  - 확인: 저장 후 빌드 경고(C4819 등)와 diff에서 글자 깨짐을 확인한다. 인코딩을 맞추려고 기존 파일을 일괄 변환하지 않는다.

## 11. 리팩터링과 기존 코드 정리

- 구조를 바꾸기 전에 빌드와 자동화 테스트로 기준선(통과·실패·크래시 목록)을 기록한다. 이미 실패하던 항목은 이유와 함께 구분한다.
- 동작이 바뀌지 않는 변경(파일 분리, 이름 변경)과 동작을 바꾸는 변경을 섞지 않고, 단계마다 빌드와 회귀 검사를 거친다.
- 멤버 선언 순서·공개 visibility·직렬화 정보를 무심코 바꾸지 않는다. 콜백 전후 검증과 cleanup 순서를 보존한다.
- 조건문을 다시 쓸 때는 평가 순서, 실패 메시지의 우선순위, 실패 시 정리 순서가 같은지 확인한다. 바꿨다면 변경 설명에 남긴다.
- 파일을 옮기거나 이름을 바꾸면 adaptive unity를 끈 전체 unity 빌드(`-DisableAdaptiveUnity`)로 이름 충돌을 확인한다.
- 결과는 기준선과 같은 테스트 결과로 확인하고, 새 공개 진입점에는 자동화 테스트를 추가한다.
- `.clang-format`은 공백·중괄호 형식을 맡는다. 역할 분리와 유효성 보장 범위는 코드 흐름을 보고 판단한다.
