# C++ 구현 스타일

`D:/Repo-W/CL_PROJ/vit-app`에서는 작은 책임의 클래스, 함수 영역과 변수 영역의 구분, 상위 함수가 처리 순서를 보여 주는 구성을 참고한다. 해당 프로젝트의 표기법이나 표준 라이브러리 선택을 Unreal 코드로 옮기는 기준은 아니다.

- Unreal의 U/A/F 접두사, PascalCase, `b` boolean 접두사, UCLASS/UFUNCTION/UPROPERTY, 엔진 컨테이너·문자열·포인터를 유지한다. 가독성 정리를 이유로 C 스타일, snake_case, `std::` 컨테이너로 바꾸지 않는다.
- 공개 클래스·함수, BP 노드, JSON 필드·이벤트 이름은 호환 계약이다. 이름만 정돈하려고 변경하지 않는다. 내부 지역 변수와 helper 이름은 실제 역할이 드러나도록 작성한다.
- 한 파일은 하나의 기능 책임을 표현한다. 작은 전용 Builder는 생성 대상과 함께 둘 수 있지만 Behavior 파일에 서로 다른 Gizmo 구현을 모으지 않는다. 공개 header 분리 시 기존 include 사용자의 호환성도 고려한다.
- 함수 하나는 한 가지 역할을 맡는다. 상위 함수는 검증·조회·처리 함수의 실행 순서를 조율할 수 있다.
- 일반 함수는 header에 선언하고 `.cpp`에서 정의한다. 짧은 Getter/Setter도 클래스 본문에 구현하지 않는 것을 기본으로 한다. 성능을 추측하여 `inline`·`FORCEINLINE`을 추가하지 않으며 명시적인 인라인화는 사용자가 필요에 따라 결정한다.
- 위 규칙은 소스 구성 원칙이다. 컴파일러의 자동 인라인 최적화를 막기 위해 `FORCENOINLINE`이나 최적화 비활성화 옵션을 추가하지 않는다. template·`constexpr` 등 사용 지점에 정의가 필요한 경우에는 해당 언어 계약을 유지한다.
- Mode의 초기화·등록, 복제의 캡처·생성·복원, UI의 구성·갱신, JSON의 파싱·직렬화처럼 함께 읽어야 하는 단위를 분리한다. 한두 문장을 감추기 위해 helper를 늘리지 않는다.
- 함수 이름에 And/Or로 서로 다른 동작을 묶지 않는다.
- 선행 조건 검사와 필요한 대상 조회를 앞에 배치하고, 검증된 데이터를 사용하는 실제 처리는 아래에 둔다.
- 같은 동기 호출 흐름에서 이미 보장된 유효성은 내부 처리 함수에서 다시 검사하지 않는다.
- 공개 진입점, 프레임을 넘긴 참조, Blueprint 콜백·재컴파일 등 수명이 달라지는 경계에서는 필요한 검사를 유지한다.
- 스폰·트레이스 등 실행 결과는 실행 후 검사한다. 종료·실패 경로의 필수 정리를 생략하면서까지 검사를 앞으로 옮기지 않는다.
- 정상적인 부재는 조기 반환, 복구 가능한 설정 오류는 ensureMsgf 후 반환, 내부 불변 조건은 check를 사용한다.
- if/for/while에는 중괄호를 사용하고 return/continue/break는 별도 줄에 둔다.
- 실패 이유나 필요한 정리가 다르면 조건을 별도 guard로 풀어 쓴다. 짧고 하나의 의미인 논리식·기본값 선택까지 기계적으로 여러 함수로 늘리지 않는다. 조건을 나눌 때 short-circuit 평가와 부수 효과의 순서를 보존한다.
- 선행 조건, 대상 조회, 실제 처리, 결과 반환을 의미 단위의 빈 줄로 구분한다.
- 전방 선언 → Delegate 선언 → 클래스 순서를 따른다. 클래스 내 함수 영역 다음 변수 영역을 배치한다.
- 각 함수 접근 지정자에서는 생성자 예외를 제외하고 virtual → 일반 함수, UFUNCTION 우선 순서로 정렬한다.
- 함수 선언 블록 사이에는 빈 줄을 한 줄 둔다. UFUNCTION은 함수 선언에 바로 붙이고, 함수 설명 주석이 있으면 주석 앞에 빈 줄을 두어 주석·UFUNCTION·함수를 한 블록으로 묶는다.
- 각 그룹은 초기화·세팅·진입 → 업데이트·갱신 → 삭제·리셋 → On 바인딩 → Getter/Setter 순서로 정리한다.
- public using 다음에 기본 생성자를 배치한다. 변수는 UPROPERTY 우선, 포인터 → 사용자 정의 타입 → 프리미티브 순서로 정리한다.
- 자체 멤버 기본값은 선언 순서와 같은 생성자 초기화 리스트로 작성한다.
- 기존 코드 정리 시 멤버 선언 순서·공개 visibility·직렬화 정보를 무심코 바꾸지 않는다. 콜백 전후 검증과 cleanup 순서를 보존하고 실제 회귀 검사로 확인한다.
- 주석은 수명·실패 정리·호환성 등 코드만으로 알기 어려운 이유를 설명한다. 함수 이름을 반복하는 주석과 빈 장식 구분선을 늘리지 않는다.

함수 선언 간격 예시:

```cpp
UFUNCTION(BlueprintCallable)
void UpdateSelection();

/** 저장된 선택 상태도 함께 초기화한다. */
UFUNCTION(BlueprintCallable)
void ResetSelection();
```

`.clang-format`은 공백·중괄호 형식을 유지한다. 역할 분리와 유효성 보장 범위는 코드 흐름을 보고 판단한다.
